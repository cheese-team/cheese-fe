# Frontend Code Convention

## 1. 기본 원칙

- React, Next.js, TypeScript의 공식 권장 방식을 우선한다.
- 가독성과 유지보수성을 우선하며, 불필요한 추상화는 지양한다.
- ESLint와 Prettier로 관리할 수 있는 스타일은 별도의 컨벤션으로 중복 관리하지 않는다.

## 2. 파일 및 네이밍

- React 컴포넌트는 PascalCase를 사용한다.
- 유틸리티, 타입, 일반 API 파일은 camelCase를 사용한다.
- page.tsx, layout.tsx, route.ts 등 Next.js App Router에서 정의한 예약 파일은 프레임워크의 파일명 규칙을 따른다.
- 변수와 함수는 camelCase를 사용한다.
- 변경되지 않는다는 의미를 강조하는 모듈 수준의 고정 상수는 UPPER_SNAKE_CASE를 사용한다.
- 타입은 PascalCase를 사용한다.
- boolean 값은 `is`, `has`, `can`, `should` 등 의미를 명확히 나타내는 접두사를 사용한다.

## 3. 컴포넌트

- 여러 페이지에서 재사용되는 컴포넌트는 `src/components/common`에서 관리한다.
- 특정 도메인에서만 사용하는 컴포넌트는 해당 도메인 내부에서 관리한다.
- 기존 공통 컴포넌트로 구현 가능한 경우 동일한 역할의 컴포넌트를 새로 만들지 않는다.
- 컴포넌트가 지나치게 많은 UI와 비즈니스 로직을 담당하지 않도록 책임을 분리한다.

## 4. React

- 렌더링 과정에서 계산할 수 있는 값은 불필요하게 state로 관리하지 않는다.
- 다른 state나 props에서 계산할 수 있는 값은 가능한 한 파생 값으로 처리한다.
- `useEffect`는 외부 시스템과의 동기화가 필요한 경우를 중심으로 사용한다.
- `useEffect`를 단순 state 동기화 목적으로 사용하는 것은 지양한다.

## 5. TypeScript

- 명확한 타입을 정의할 수 있는 경우 `any` 사용을 지양한다.
- 컴포넌트 Props는 타입으로 명확하게 정의한다.
- API 요청 및 응답 데이터의 타입을 명확하게 정의한다.
- 불필요한 타입 단언(`as`)은 지양한다.

## 6. Next.js

- App Router의 파일 및 라우팅 규칙을 따른다.
- Client Component가 필요한 경우에만 `'use client'`를 사용한다.
- Client Component의 범위를 불필요하게 넓히지 않는다.
- 페이지 컴포넌트에 복잡한 로직이 집중되지 않도록 필요한 경우 컴포넌트나 로직을 분리한다.

## 7. 스타일

- 프로젝트에서 정의한 디자인 토큰을 우선적으로 사용한다.
- 기존 토큰으로 표현 가능한 값을 새로운 토큰으로 중복 정의하지 않는다.
- 공통 UI는 기존 공통 컴포넌트와 스타일을 우선적으로 활용한다.

## 8. API 및 서버 상태

- API 요청 로직과 UI 로직의 책임을 분리한다.
- 서버 상태는 React Query를 통해 관리하는 것을 우선한다.
- 서버 상태를 불필요하게 별도의 로컬 state로 복제하지 않는다.
- mutation 이후 관련 데이터의 캐시 갱신이 필요한지 확인한다.

## 9. CodeRabbit 리뷰 기준

CodeRabbit은 PR 리뷰 시 다음 항목을 확인한다.

### 반드시 확인할 항목

- PR 제목이 `<type>: <작업 내용>` 형식인지 확인한다.
- 컴포넌트 이름이 PascalCase인지 확인한다.
- 변수와 함수 이름이 camelCase인지 확인한다.
- 유틸리티, 타입, 일반 API 파일명이 camelCase인지 확인한다. 단, page.tsx, layout.tsx, route.ts 등 Next.js 예약 파일은 프레임워크 규칙을 따른다.
- 타입 전용 import에 `import type`이 사용되었는지 확인한다.
- 현재 작업과 관계없는 변경 사항이 PR에 포함되었는지 확인한다.
- 하나의 PR에 서로 무관한 작업이 과도하게 혼합되었는지 확인한다.

### 개선 의견으로 제안할 항목

- import 그룹 순서가 크게 어긋나 가독성이 떨어지는 경우
- 컴포넌트의 공개 API가 불필요하게 많은 내부 구현을 노출하는 경우
- 컴포넌트 구조상 순환 참조가 발생할 가능성이 있는 경우

### 리뷰하지 않아도 되는 항목

- Prettier가 자동으로 처리할 수 있는 단순 줄바꿈이나 공백
- ESLint가 이미 명확하게 검출하고 있는 동일한 포맷 문제
- 현재 PR에서 수정하지 않은 기존 코드의 사소한 컨벤션 문제
- 기능과 유지보수성에 영향을 주지 않는 개인 취향 수준의 표현 차이
